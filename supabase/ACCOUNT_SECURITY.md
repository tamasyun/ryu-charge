# 認証・アカウント設定の導入手順

ソース追加だけではリモートのDB・Auth・Edge Function・配信サイトは変わりません。検証用プロジェクトで確認し、承認された段階で以下を適用してください。管理用Secret Keyを `VITE_` 環境変数やソース、GitHubに保存しないでください。

## 1. DBの追加設定

既存の `20261105164718_add_nickname_profiles_and_authorship.sql` 適用済みのDBを前提とします。現在のテーブル・外部キー・ポリシーを確認してバックアップし、`migrations/20261106055819_account_security_and_deletion.sql` を適用します。Supabase DashboardのSQL Editorで内容を確認して実行するか、利用中のCLIバージョンのヘルプに従って適用してください。

追加する内容：

- 公開APIに露出しない `account_private` スキーマに初回パスキー登録権・削除確認証のハッシュ・削除ジョブを保存。RLS有効、一般ユーザーのアクセスなし。
- 初回メール確認時だけ登録権を作り、プロフィール完成後に一度だけ消費。10分以内の新規登録の完了処理でのみ自動登録を試す。期限切れ・キャンセル後も設定から手動登録できる。
- `profiles.nickname` の既存の1〜20文字制約と本人UPDATEポリシーは変更しない。
- 削除開始後はDBのトリガーでプロフィール・レビュー・設備の書き込みとStorageへの追加を停止。未失効JWTについてもユーザーと `auth.sessions` の存在を確認する。
- `auth.users` 削除時のトリガーで、外部キーのない `room_reviews.user_id` を明示的に削除。`rooms` / `outlets` は残して `user_id` をNULLにする。
- 現在の外部キーにより、プロフィール、Authのパスキー・セッション、`room_photos` の本人行はCASCADE削除される。既存の設備の外部キーはSET NULLのまま維持。
- `review-images` の既存アップロード許可にRESTRICTIVEポリシーを追加し、本人・大学メール・プロフィール・有効セッションを要求する。既存の認証済みアップロード経路とファイル名は維持する。
- 特権RPCは `service_role` だけ実行可能。`is_active_account()` と `claim_initial_passkey_enrollment()` は本人の状態だけを扱い、`authenticated` に限定する。

このSQLだけで空のDB全体を構築するものではありません。ロールバックで削除済み写真やアカウントは復元できません。

## 2. Supabase Authのパスキー設定

[公式手順](https://supabase.com/docs/guides/auth/passkeys)に従い、Authentication → Passkeysで有効化します。

- Relying Party Display Name：`琉CHARGE`
- Relying Party ID：本番ホストの `ryu-charge.vercel.app`（スキーム、ポート、パスは含めない）
- Relying Party Origins：`https://ryu-charge.vercel.app` など、実際に認証を提供するOriginを完全一致で登録

RP IDは登録済みパスキーが結び付く識別子です。後で変えると既存パスキーが使えなくなるため、独自ドメインへ移す予定がある場合は先に決定してください。プレビュー用のランダムなホスト名を本番のRPとして使わないでください。

ローカル確認には別の検証用Supabaseプロジェクトを使い、RP IDを `localhost`、Originを `http://localhost:5173` にします。本番ドメインのRPに無関係な `localhost` や `127.0.0.1` を混ぜることはできません。通常はHTTPSが必要で、loopbackのみHTTPが許可されます。Turnstileの設定はREADMEの手順も参照してください。

`supabase-js 2.117.3` はAPIが既定で有効なのでSDKのExperimentalフラグは不要です。Supabase側が未設定・非対応でもメールOTPは残り、パスキー操作時にエラーを案内します。端末の秘密鍵・生体情報はアプリで取得しません。

## 3. delete-account Edge Function

`functions/delete-account/index.ts` を、DBを適用した同じプロジェクトに配備します（関数名 `delete-account`）。Supabase CLIの `functions deploy --help` を確認し、対象プロジェクトを明示して配備してください。

必要な**サーバー側**環境変数：

| 変数 | 用途 |
|---|---|
| `SUPABASE_URL` | 同じプロジェクトのAPI URL |
| `SUPABASE_ANON_KEY` | OTP検証用の分離クライアント。Edge Functionの標準環境変数 |
| `SUPABASE_SERVICE_ROLE_KEY` | Storage・Authユーザー削除と特権RPC。Edge Functionの標準サーバー環境変数 |
| `ACCOUNT_ALLOWED_ORIGINS` | `https://ryu-charge.vercel.app` など。複数はカンマ区切り。ワイルドカードなし |

既定の `SUPABASE_*` はSupabaseのEdge Function実行環境が提供する値を使います。実際の鍵をフロントエンドやサンプルファイルへコピーしないでください。独自の管理用Secret Keyを使う構成へ変える場合も、必ずサーバー側だけで扱います。

`config.toml` の `verify_jwt = false` は新しい署名鍵への対応のためです。代わりに**すべての操作で**関数内の `admin.auth.getUser(AuthorizationのJWT)` が本人を検証します。公開キーや呼び出し本文の `userId` だけでは削除できません。認証を行うこの処理を削除しないでください。

削除の流れ：

1. アプリが本人メールへOTP送信。Turnstileが設定済みなら新しいトークンが必須。再送信は60秒待つ。
2. Edge Functionが、そのJWTの本人メールに対して8桁OTPを検証。検証専用の一時セッションはサーバー内で失効させ、ブラウザーのログイン保持設定を変更しない。
3. ランダムな確認証を発行し、DBにはSHA-256ハッシュだけ保存。本人のIDに結び付け、5分で失効する。ブラウザーではメモリ内だけに持つ。
4. チェックボックスと「削除する」の入力後、最終削除要求を送る。サーバーも確認文と確認証を必ず検証する。
5. 削除ジョブを記録して書き込みを停止し、Storageの削除対象を固定。レビュー画像URLのページングとStorageの所有者情報の両方を使い、投稿に結び付かなかった本人の写真や別バケットの所有オブジェクトも回収する。
6. Storage APIで写真を削除した後、`auth.admin.deleteUser(id, false)` でAuthユーザーを削除。DBトリガーと既存のFKにより関連データを同じトランザクションで削除・匿名化する。Storageメタデータを直接SQLで削除しない。
7. 成功後はブラウザーのセッションを除去し、ログアウト表示へ戻る。保存済みlocalStorage・sessionStorageはサインアウトAPI失敗時も消す。

## 4. 途中失敗・復旧

StorageとAuthは単一トランザクションにできません。写真の一部が削除された段階で失敗する場合があります。Storage削除が失敗した場合はAuth削除へ進まず、プロフィール・レビュー・Authユーザーと削除対象の一覧を残します。ユーザーはログイン状態を保ったまま同じ画面から再試行できます。5分を過ぎた確認証は、新しいOTPで本人確認し直します。

並行実行は2分のリースで抑止し、異常終了時もリースは期限切れで再試行できます。削除開始後の新規投稿を防ぐトリガーは再試行まで有効です。管理者が単純に削除ジョブを消して投稿を再開させると、一部だけ削除された状態になるため、まずStorageの障害・権限・関数ログを調べ、削除を完了させてください。

本人所有と確定できるStorageオブジェクトは削除します。過去の所有者なし画像は、本人レビューだけに参照される同じプロジェクトの `review-images` オブジェクトに限定します。他ユーザーが所有・参照する画像や外部URLは巻き込まず保持します。由来が不明な過去の匿名・共有画像は管理者による確認が必要です。

削除成功後に通信が切れた場合は、画面が結果を確認できないことがあります。次の要求でセッション無効が分かったときは保存済みセッションを消しますが、未確認の削除結果を成功とは表示しません。他の端末の更新トークンはAuthユーザーとともに失効し、既発行JWTによる追加投稿もDBのアクティブ判定で拒否されます。

## 5. 検証

`npm test` は既存OTP・保持設定に加え、パスキーと設定画面、削除ハンドラーの認可・OTP・写真削除失敗・ページング・削除順序を検証します。SQLは開発専用依存のPGlite（隔離したPostgreSQLエンジン）で実行し、本人以外の更新拒否、初回権利の一度限りの消費、写真削除前のAuth削除拒否、再試行、レビュー・プロフィール・パスキー・セッションの削除と設備の維持を確認します。ホストDBや本番DBには接続しません。

実サービスの設定を変更せずに行うテストなので、Supabase Authとの実際のWebAuthn通信・実メール配送・Storage実体・実プロジェクトの権限の結合確認は別途必要です。PGliteでは実際の並列セッションやSupabase管理ロールの動作を再現していません。

### iOS Safariでの実機確認項目

- 本番と同じHTTPS/RP IDで、新規登録のOTP → プロフィール作成 → 事前案内なしの端末登録画面まで進む。
- 登録をキャンセル、または操作制限で開かない場合もログインしたままで、通常ログイン・再読込で再表示されない。
- ユーザー名 → 設定 → 「パスキーを登録」の直接タップで標準画面が開く。手動登録前には一覧の再取得など余分な通信を挟まない。
- パスキーログイン、保持設定、名前変更、一覧、削除、メールOTPへの切替が動く。
- 狭い画面・ソフトウェアキーボード表示中でもスクロールでき、操作ボタンや最終確認が隠れて操作不能にならない。

自動登録はOTP・プロフィールの非同期処理後に呼ぶため、Safariでユーザー操作の権利が失われる場合があります。[WebKitの説明](https://webkit.org/blog/11312/meet-face-id-and-touch-id-for-the-web/)に沿い、拒否を捕捉して強制・自動再試行はせず、ログインを維持して設定からの直接操作を用意しています。Safari風のUser-Agentだけのテストを、iOS実機の生体認証検証とは扱いません。
